## 3. 根因：完整数据流追踪

### 3.1 源头：WeChat 编辑器 HTML

微信公众号文章用「图片 + 加粗文字 + 图片」的组合来模拟章节标题，因为 WeChat 编辑器不支持直接用 `<h2>` 标签。

原始 HTML 大致为：
```html
<img src="..."/>
<strong><strong>热物理性质：密度与热容的组分主导因子</strong></strong>
<img src="..."/>
```

不同文章的 `<strong>` 嵌套深度不同（1层～4层），取决于：
- 作者在编辑器里重复点了多少次加粗按钮
- 从 Word/其他编辑器粘贴带来的冗余 `<b>` + `<strong>` 叠加
- WeChat 编辑器不同版本的行为差异
- 部分 `<strong>` 内包含 `<br>` 换行，产生断裂的配对

### 3.2 环节一：`downloader.py` 的 `markdownify` 转换

**关键代码** — `src/downloader.py:263-284`：
```python
md_content = md(str(element_copy), heading_style="atx",
                bullets="-", convert=['p', 'ul', 'ol', 'li', 'br', 'hr', 'em', 'strong'])
```

`markdownify` 将每个 HTML `<strong>` 忠实地转为一个 `**` 对。嵌套 N 层 `<strong>` → `**` × N。所以：

| HTML | markdownify 输出 |
|------|------------------|
| `<strong>text</strong>` | `**text**` (2星/侧) |
| `<strong><strong>text</strong></strong>` | `****text****` (4星/侧) |
| `<strong><strong><strong>text</strong></strong></strong>` | `******text******` (6星/侧) |
| 4层嵌套 | `********text********` (8星/侧) |

对于混合/断裂嵌套（如行30），`markdownify` 也原样保留，产生 `******...****...******` 的不对称模式。

### 3.3 环节二：`translator.py` LLM 翻译

**关键代码** — 系统提示词要求 LLM "**Keep Markdown markup (#, **, >, etc.) — translate only the text**"

LLM 保持了 `**` 标记不动，只翻译内部文字。因此翻译后的 `_en.md` 保留了完全相同的星号数量和模式。

但 LLM 是非确定性的——它可能把 `图N` 改写成 `Figure N`、移动星号位置等，见已记录的问题。

### 3.4 环节三：`converter.py` 博客格式转换

**关键代码** — `src/converter.py:556-627` (`_fix_image_layout` + `_inline_text_to_heading`)：

```python
def _inline_text_to_heading(self, text: str) -> str:
    had_bold = False
    while text.startswith('**') and text.endswith('**'):
        had_bold = True
        if text.startswith('****'):
            text = text[4:]
        elif text.startswith('**'):
            text = text[2:]
        if text.endswith('****'):
            text = text[:-4]
        elif text.endswith('**'):
            text = text[:-2]
        text = text.strip()
    if had_bold:
        return f'## {text}'
```

这个 while 循环不断剥去首尾的 `**` 或 `****`，直到文本不再以 `**` 为首尾。例如：

- `****text****` → 去4首4尾 → `text` → 输出 `## text` ✅
- `******text******` → 去4首4尾 → `**text**` → 去2首2尾 → `text` → `## text` ✅
- `********text********` → 去4首4尾 ×2 → `text` → `## text` ✅

**但行16和行30这类"中间夹带非加粗文本"的情况，只能剥离出最外层文本**。行16 "精度" 能正确提取，但尾部的 `****` 在 `_fix_image_layout` 的行分割过程中可能被识别为另一段；而行30的 `******微观结构解析：****Th⁴⁺配位环境的阳离子极化调控******` 在分割后只得到 `微观结构解析：`（前6个星号被匹配到该段）。

## 4. 影响范围评估

### 4.1 对博客输出的影响

`converter.py` 的 `_inline_text_to_heading` 方法已经能处理**标准对称嵌套**（行41、53、70、73），将它们正确转换为 `## text` 标题。

**已知不能完美处理的场景**：
- **行30 混合断裂嵌套**：`******微观结构解析：****Th⁴⁺配位环境的阳离子极化调控******` — 中间的 `****` 无法被 while 循环清理（因为 while 只看首尾）
- **行16 尾部孤立星号**：`****精度****DP模型：...****` — 尾部 `****` 没有配对的文本内容

### 4.2 对翻译质量的影响

LLM 在看到混乱的星号时可能有以下行为：
- 把 `******...******` 误认为特殊标记而跳过翻译
- 尝试"修复"星号配对（但不一定成功）
- 某些 LLM 会去掉多余的星号（这是好事）

## 5. 可能的解决方案

待「感知哈希图片筛选」优化完成后，可考虑以下修复方案：

### 方案 A：下载阶段归一化（推荐）
在 `downloader.py` 的 `markdownify` 之后，对 `**` 序列做后处理：
- 将所有连续 `**` 序列归一到 1 对 `**`（即 `****` → `**`，`******` → `**`）
- 清理孤立/不成对的 `**`

### 方案 B：转换阶段增强
增强 `converter.py` 的 `_inline_text_to_heading` 方法：
- 不只检查首尾，而是对整个文本段做正则替换：`re.sub(r'\*{2,}', '**', text)`
- 增加对"中间夹带非加粗文本"的处理

### 方案 C：借助感知哈希筛选间接解决
图片筛选（感知哈希）可以过滤掉装饰图片，可能改变 `![图N] + bold + ![图N]` 的排版结构。等筛选完成后，可能部分异常模式会自然消失或变得更容易处理。
