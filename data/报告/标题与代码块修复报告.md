## 1. 正文标题被拍平（起点问题）

### 现象

用户报告：博客成文的第一段没有标题。原文第一节标题
「精度比肩主流模型，速度超越经验势；DPA4 OMat24、OMol25 预训练模型同步亮相」
在 `_zh.md` 里变成了正文的一部分，且和后面的段落**粘在同一行**：

```
****精度比肩主流模型，速度超越经验势；DPA4 OMat24、OMol25 预训练模型同步亮相****一块新材料能不能扛住高温、一颗电池会不会鼓包……
```

### 定位过程

用户最初怀疑是「星号加粗去除」或「标题前后图片过滤」两个历史优化之一造成的。
实际抓取源站 HTML 后发现，该标题在原文中是货真价实的 `<h1>` 标签：

```html
<h1 style="font-size: 17px;..."><span><strong>精度比肩主流模型…</strong></span></h1>
```

根因在 `downloader.py` 调用 markdownify 时的白名单：

```python
convert=['p', 'ul', 'ol', 'li', 'br', 'hr', 'em', 'strong']
```

markdownify 的 `convert` 是**白名单语义**——不在列表里的标签，标签本身被丢弃、只保留内部文字。
`h1`~`h6` 不在列表里，于是 `<h1>` 被剥掉，只剩内层 `<strong>` 转成的 `****…****`。

而微信正文的段落是 `<section>`（同样不在白名单、且无块级语义），所以标题和正文之间
**一个换行都没有**，被直接粘成一行。用 markdownify 单独复现，输出与故障文件完全一致：

```
现状：  '**SUBTITLE**Body text starts here.'
加 h1： '\n\n# **SUBTITLE**\n\nBody text starts here.'
```

**影响范围**：这篇文章的 8 个标题全部被压平，不止用户发现的第一个。

### 为什么翻译后标题彻底消失

翻译 prompt 硬性要求「输出第一行必须是 `# 标题`」。模型看到正文第一行是加粗的
`****精度比肩…****`，就把它提升为 H1 当作文章标题，于是正文里这句话没了。

审校报告其实已经报了 2 条 ACCURACY 指出「用了第一个加粗副标题当主标题」，
但分数 85 分判定 PASSED，被放过去了。

### 修复

`downloader.py:287,313` 两处 markdownify 调用的白名单加入 `h1`~`h6`。

新增 `_clean_headings()`（`downloader.py:615`）处理转换后的残留：

- 去掉标题内的 `**` 包裹（`# ****使用教程********（Bohrium + MatMaster）****` → `# 使用教程（Bohrium + MatMaster）`）
- 丢弃源站当间距用的空 `<h1>`
- 把塞进 `<h1>` 的纯图片还原成普通图片行
- 围栏代码块内部原样保留（块内的 `#` 是 shell 注释，不是标题）

## 2. 代码块被拍平

### 现象

修好标题后，`_zh.md` 里出现一行异常的「标题」：

```
# DPA4：训练 / 微调 / 冻结 / 评估 / 压缩dp --pt train input.jsondp --pt train finetune.json --finetune pretrained.pt……
```

核对修改前的旧文件确认，这一行在原来的第 125 行就已经是 `#` 了，属于**独立的既有缺陷**，
不是标题修复引入的回归。

### 原因

微信的代码块结构是三个问题叠加：

```html
<pre class="code-snippet__js">
  <code># DPA4：训练 / 微调 / 冻结 / 评估 / 压缩</code>
  <code>dp&nbsp;--pt train input.json</code>
  ...
</pre>
```

1. `pre` / `code` 不在 markdownify 白名单 → 标签被剥掉，只剩纯文本
2. 每行代码是一个独立 `<code>`，**彼此之间没有换行符** → 16 行代码粘成一整行
3. 行内空格是 `\xa0`（不换行空格），不是普通空格

拍平后代码块第一行的 shell 注释 `#` 正好落在行首，被当成了 Markdown 标题。

### 修复

沿用项目已有的占位符模式（与公式、图片的处理方式一致）：

- `_extract_code_text()`（`downloader.py:574`）：按 `<code>` 逐行还原，`\xa0` 复原成普通空格，去掉首尾空行
- `_replace_code_blocks()`（`downloader.py:598`）：markdownify 之前把 `<pre>` 换成 `[CODE_PLACEHOLDER_N]`，转换完再还原成围栏代码块。顺序上放在公式/图片提取**之前**，避免误伤块内内容
- `has_nested` 判断加上 `has_pre`，否则纯代码块的 section 走不进占位符分支

### 自纠

修复过程中发现自己引入了新缺陷：`_clean_headings` 会误伤代码块内容——把块内 shell
注释的 `****` 剥掉、把单独一行的 `#` 整行删掉。已改为围栏感知，块内原样保留。

## 3. 正文标题层级全是 H1

### 用户提问

「读取的标题全是 H1 是什么原因？文章题目是 H1，标题不应该是 H2 吗？是微信链接的原因吗」

### 结论：是微信原文如此

抓取源站 HTML 确认，正文 div 内的标题标签本来就是 `h1`：

| 源站标签 | 内容 |
|----------|------|
| h1 | 精度比肩主流模型，速度超越经验势… |
| h1 | DPA4：把高精度推到无机材料与复杂分子的两端 |
| h1 | DPA4C：世界最快的通用机器学习势 |
| h1 | 使用教程（Bohrium + MatMaster） |
| h3 | 1. 通过网页或 Bohrium CLI 提交计算 |
| h3 | 2. 用自然语言在MatMaster上完成DPA4/DPA4C全流程 |
| h1 | 相关链接 |

这篇用 **135editor** 排版（HTML 里有 `label="edit by 135editor"`）。这类微信编辑器的
「小标题」组件用什么标签取决于模板作者——微信正文的显示效果由内联 `style` 决定
（这个 `<h1>` 上写死了 `font-size: 17px`），标签语义基本没人管。

文章标题 `单卡千万原子…` 也是 `<h1>`（`class="rich_media_title"`），但它在
`js_content` **外面**，属于页面框架，downloader 通过 `og:title` meta 单独提取。

### 修复

原文层级是 h1 和 h3 混用、**跳过了 h2**。因此没有采用简单的「整体 +1」
（那样 h3 会变成 `####`，留一个空档），而是按出现过的层级**排名**映射成连续序列：

```
h1 → ##
h3 → ###
```

修复后正文最高只到 `##`，H1 唯一地留给文章标题（由 `_save_markdown` 在
`_clean_headings` 之后写入，不受降级影响）。

## 4. `max_tokens` 对推理模型过低（deepseek 事故根因）

### 现象

用户切换到 deepseek 后，产出 331 字节的空文件：

```
✓ 翻译完成: 8623 字
- 质量分数: 0/100      ❌ 未通过
✓ 修改完成: 0 字        ← revise 返回空串
⚠️ LLM 输出缺少 # 标题行，回退到中文原标题
```

用户问：「是不是 deepseek 的问题？」

### 隔离测试

写脚本只调用 `translate_markdown` 的底层 API，捕获**未经清理的原始返回**：

```
finish_reason      : length
completion_tokens  : 16000
  └ reasoning_tokens: 16000     ← 全部是思维链
raw length         : 0          ← 正文 0 字
```

`reasoning_tokens` 等于 `completion_tokens`，说明模型把全部预算花在内部思维链上，
还没开始写正文就被 `max_tokens` 掐断。API 正常返回（HTTP 200），但 `content` 是空串。

### 对照实验推翻了初步结论

用户追问「为什么 qwen 可以」。用**同一份输入**跑 qwen 对照：

| 字段 | deepseek-v4-pro | qwen3.7-max |
|------|-----------------|-------------|
| finish_reason | length | stop |
| completion_tokens | 16000（顶格） | 15788 |
| reasoning_tokens | 16000 | **10530** |
| raw length | 0 | 21112 |

**qwen 也是推理模型**，也烧了 10530 个思维链 token。最初「qwen 不是推理模型所以安全」
的判断是错的。真正的区别是思维链占比：

```
deepseek: 16000 思维链 +    0 正文 = 16000  → 撞上限
qwen    : 10530 思维链 + 5258 正文 = 15788  → 仅剩 212 token 余量（1.3%）
```

qwen 不是安全，是**险胜**。文章再长几百字，qwen 会掉进同样的坑。

### 修复

实测两家 API 都接受到 131072，故新增两个类常量替换 6 处硬编码：

```python
MAX_TOKENS_LONG = 64000   # 翻译 / 修改：需要完整输出长文
MAX_TOKENS_JSON = 32000   # 审核：只输出 JSON，但思维链同样占额度
```

### 复测

同一篇文章、同一份输入，只改 `max_tokens`：

| | 修复前 | 修复后 |
|---|--------|--------|
| finish_reason | length | stop |
| 输出长度 | 0 字 | 20490 字 |
| 围栏 | — | 4（完整） |
| 代码块 | — | 16 行 + 6 行，NBSP 已清理 |

残留的 12 个中文字符全是图片 alt 文本 `![图N](...)`，prompt 明确要求原样保留，属正确行为。

## 5. 空返回无保护

`translate_markdown` / `revise_translation` 原先直接取 `response.choices[0].message.content`，
空串会一路写进文件、覆盖好内容。

新增 `_extract_content()`（`translator.py:77`）：检查 `finish_reason` 和空内容，
空返回直接抛错并说明原因：

```
翻译: 模型返回空内容 [finish_reason=length]（思维链占用 16000 tokens，
耗尽了 max_tokens 额度；请调大 max_tokens 或改用非推理模型）
```

非空但被截断的情况只警告、不中断。

## 7. `clean_llm_response` 吃掉围栏（潜伏缺陷）

`utils.py` 原逻辑无条件剥离首尾的 ` ``` `：

```python
if content.endswith('```'):
    content = content[:-3]
```

实测损坏场景：

```
LLM 输出 tail : '```\ndp --pt train input.json\n```'
清理后    tail : '```\ndp --pt train input.json'      ← 闭合围栏被吃掉
```

极端情况下会把内容剥成空串：`'```\n```'` → `''`。

**修复**：剥离后检查围栏数量奇偶性（`utils.py:98`），若变成奇数说明删掉的不是包裹层
而是正文自己的围栏，保持原样。

| 输入 | 修复前 | 修复后 |
|------|--------|--------|
| 以代码块结尾 | 闭合围栏被吃掉 | 完整保留 |
| 以代码块开头 | 开头围栏被吃掉 | 完整保留 |
| 真的被 ` ```markdown ` 包裹 | 正确剥离 | 正确剥离 |

**此前从未触发**，因为代码块被拍平时 `_zh.md` 里一个围栏都没有。

## 8. prompt 被正文围栏截断（潜伏缺陷）

`review_translation` / `_cross_review` / `revise_translation` 三处 prompt 都用
` ``` ` 包裹原文：

```
**Chinese Original**:
```
{zh_content}      ← 正文含有 4 个 ```
```
```

正文里第一个 ` ``` ` 出现时，外层包裹被**提前闭合**，模型看到的是结构错乱的 prompt。

**修复**：换成不会与 Markdown 冲突的 XML 风格分隔符
`<CHINESE_ORIGINAL>` / `<ENGLISH_TRANSLATION>`。

同样**此前从未触发**，原因同上。

## 9. 标题问题三连（修复 1 之后暴露）

修好 `<h1>` 之后，正文里第一次出现真实的标题结构，连带暴露出三个独立的标题缺陷。
这三个是本轮反复返工最多的部分。

### 9.1 `main.py` 无条件删除第一个 H1

原代码用 `re.search(..., re.MULTILINE)` 全文搜索第一个 `#` 然后无条件删除。
`_zh.md` 现在有两个 H1（文章标题 + 第一节标题），当模型只输出一个 H1 时，
被删掉的就是**第一节标题**——用户看到的「第一节标题消失」。

**修复**：改用 `re.match` 只匹配开头那一行（`main.py:268`）。

**自纠**：第一版漏写 `re.MULTILINE`，导致 `$` 只匹配字符串末尾，正常标题反而抓不到。
测试用例暴露后修正。

### 9.2 模型吞掉标题行并提升 `##`

用户再次反馈标题丢失。这次 `_zh.md` 结构完全正确，问题出在翻译环节：

用**同一份输入**跑两次 qwen，结果不同：

| | 用户那次 | 探针 |
|---|---------|------|
| 标题数量 | 11 | 12 |
| 首行 | `# Accuracy Rivals…`（第一节） | `# 10 Million Atoms…`（文章标题） |
| 文章标题英文是否存在 | 否 | 是 |

即模型**有时**会吞掉开头的 `# 文章标题`，把正文第一个 `##` 提升成 `#` 顶替。
这是单次调用的非确定性，纯靠 prompt 约束不住。

> 此处修正了一个早先的错误判断：曾把「标题重复」归因于模型非确定性并判定
> 「不需要修」，当时只比对了首行、没检查正文里标题是否还在，结论下早了。

**修复（双保险）**：

1. prompt 收紧：明确禁止用小标题顶替文章标题，要求标题数量、顺序、层级全部不变
2. 代码兜底 `_restore_heading_levels()`（`translator.py:110`）：
   - 数量一致 → 逐个按原文层级校正
   - 译文少一个且原文首个是 `#` → 判定吞了标题，对齐剩余并调 `_translate_title()` 补译
   - 数量差异过大 → 只告警，不乱改

**自纠**：第一版判断条件写成 `en_h[0][1] == 1`（要求译文首个标题是 `#`），
但模型吞标题后首个标题本来就已是 `##`，条件不成立，正好漏掉真实场景。回归用例暴露后修正。

### 9.3 模型留着标题行但不翻译

用户第三次反馈。这次 `_restore_heading_levels` 也没起作用：

```
原文 8 个标题，译文 8 个标题  → 数量对得上
每个标题的 # 层级一一对应      → 层级无需校正
```

兜底走进「数量对得上」分支，改了 0 处直接返回。它只比对**数量和层级**，
从未检查标题**内容是否真的翻译过**——模型把 `# 单卡千万原子…` 整行照抄了。

`main.py:274` 那句 `⚠️ 标题可能未翻译（含中文）` 只打印警告、不做修复。

**修复**：在「数量对得上」分支的 `return` 之前补上内容检查
（`translator.py:152-161`）——首行是 H1 且含中日韩表意文字，就调 `_translate_title()`
补译。新增 `_has_cjk()`（`translator.py:189`）做判定。判定只看首行 H1，
不扫全文，正文残留中文不会误触发。
