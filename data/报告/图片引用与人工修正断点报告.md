## 1. 白屏故障：失效图片引用

### 1.1 现象

PR #368 推上去后，预览站点首页正常（51 KB，能列出新文章标题和链接），
但点进文章页是白屏。探测结果：

```
文章页  DeePMD-kit_2026_10_10   HTTP 200    0 bytes
对照组  DeePMD-kit_2026_07_15   HTTP 200   28854 bytes
对照组  DeePMD_2026_06_17       HTTP 200   34355 bytes
```

关键点：**不是前端渲染白屏，是这个页面的 HTML 文件本身就是 0 字节**。
而且 CI 显示 `conclusion: success`——Hexo 打了 ERROR 却仍以退出码 0 结束，
所以构建"成功"但产物是空的。

### 1.2 排查过程

走过一段弯路，记下来备查。

**第一次猜测（错误）**：注意到正文第一行是 `## Core–shell nanostructured alloys...`，
一整段几百字的导语被打上了 `##`，猜是它破坏了 Hexo 的摘要渲染。

**否证方式**：全仓库普查 96 篇文章，统计"frontmatter 后首行就是 `##`"的有 7 篇
（`2022_csi_workshop.md`、`ABACUS_13_06_2025.md`、`APEX_2026_06_22.md` 等），
逐个探测线上页面——全部正常返回 28–35 KB。假设被推翻。

**特征普查**：改为对比"这篇有、其他 95 篇没有"的特征：

| 特征 | 本篇 | 其他篇命中数 |
|------|------|--------------|
| mmbiz 图床链接 | 有 | 0 |
| img 标签内含 `&` 参数 | 有 | 0 |
| img src 内含 `#` 锚点 | 有 | 25 |
| 尖括号数字 `<112>` | 有 | 1 |
| 正文首行是 `##` | 有 | 7 |

只有前两项是独有的，指向那张 mmbiz 图。

**定论**：直接读 CI 构建日志，拿到权威错误信息：

```
ERROR Render HTML failed: DeePMD-kit_2026_10_10/index.html
Error: Parse Error: <img data-src=https://mmbiz.qpic.cn/mmbiz_png/Z8kN.../640?
wx_fmt=png&from=appmsg&tp=webp&wxfrom=5&wx_lazy=1#imgIndex=1
pic_center width="100%" height="100%" /></center>
```

### 1.3 根本原因

真正的原因不是 `&`，而是 **HTML 未加引号的属性值里不允许出现 `=`**。
那串微信图床 URL 带着 `wx_fmt=png&from=appmsg&tp=webp&wxfrom=5&wx_lazy=1`，
五个等号，解析器在第一个 `=` 处就断了。

完整因果链：

1. pic3 是文章封面图，pHash 哈希库里没有它，自动装饰图过滤器没识别出来
2. 用户在 Step 4 断点处手动把 `pic3.png` 移进了 `images/_filtered/`
3. 但两处不会跟着动：
   - `_en.md` 第 25 行的 `![图3](images/pic3.png)` 引用还在
   - `images_map.txt` 里 `pic3` 那行还在，值是微信原始 URL
     （这张图当初下载失败，所以 map 里存的是原始外链而非 OSS 地址）
4. Step 5 转换时 `image_map.get('pic3', local_path)` 命中了那个微信 URL
5. 拼成未加引号的 `<img src=https://...wx_fmt=png&...>` 写进博客文件
6. Hexo 的 `hexo-renderer-marked` 抛 Parse Error，该页产出 0 字节
7. 线上白屏

一句话：**用户只移了图片文件，但正文引用和 map 都没动，于是回退到了一个
无法安全放进 HTML 属性的外链。**

### 1.4 修复

`converter.py` — `_convert_images()` 增加 `images_dir` 参数：

- 生成 img 标签前，先查本地 `images/` 里这张图还在不在
- 不在就把整条引用删掉（对应"用户把图移进 `_filtered/`"的操作），
  不再回退到原始外链
- `images_dir` 不存在时跳过校验，避免把所有图片误判为失效
- `src` 一律加引号，URL 含 `= & #` 也不会破坏解析
- 删除引用后清理多余空行，并打印 `🧹 已移除 N 处失效图片引用: pic3`

`oss_uploader.py` — 上传失败回退原始 URL 时，打印完整 URL 并提示
"可能失效或被防盗链"，让问题在当下就可见，而不是等到线上白屏。

### 1.5 验证

用出问题的真实数据跑转换（pic3 已在 `_filtered/`，map 里仍是微信 URL）：

```
🧹 已移除 1 处失效图片引用: pic3

img 标签数   : 14
全部带引号   : True
残留 mmbiz   : False
残留 pic3    : False
未转义的裸 & : 0
```

重新推送到 PR 分支后，第二次 CI 构建日志：

```
INFO  Generated: DeePMD-kit_2026_10_10/index.html
```

Parse Error 消失。线上页面三次轮询均为 **HTTP 200 / 45726 bytes**，恢复正常。

## 2. 标题钩子被丢弃

### 2.1 现象

中文标题：

```
DP还能干这个？深度学习势揭示AgPd纳米合金表面位错形核与原子重排机制
```

译出来是：

```
Deep learning potential reveals surface dislocation nucleation in AgPd
Nanoalloy during atomic rearrangement
```

开头那个反问句"DP还能干这个？"整个没了。而本博客既有文章的house style是保留它的，
例如 `DeePMD_05_12_2024.md`：

```
What Can DP Do too? | Using Machine Learning to Explore the Catalytic
Kinetics of Metal Nanoclusters under Confinement Conditions
```

这类标题是"口语化钩子问句 + 技术副标题"的两段式结构，钩子是文章的灵魂，
拍平成一个干巴巴的技术短语就丢了味道。

### 2.2 修复

`translator.py` 两处 prompt 都加了规则——注意**必须改两处**，
因为标题补译走的是独立的小请求，只改主 prompt 会在兜底路径上漏掉：

1. `translate_markdown()` 的 `system_prompt`：新增 `TITLE — keep the hook:` 段，
   说明两段式结构、给出 `X还能干这个？` → `What Can X Do Too?` 的house style映射、
   附带 `没想到吧？` → `Who Knew?` 等同类钩子，并明令禁止拍平或丢弃钩子
2. `_translate_title()` 的 system prompt：同一规则的压缩版

### 2.3 局限

这是 prompt 级约束，模型仍可能不遵守。真正的硬保证需要代码兜底
（检测到中文标题含钩子模式、而译文无问号时重翻或套模板）。
本轮未加，先观察 prompt 的实际效果。

本篇文章的标题由人工定为：

```
What Can DP Do Too? Atomic-Scale Dislocation Nucleation in AgPd Nanoalloys
via Deep Learning Potential
```

## 3. 人工修正断点说明

### 3.1 问题

流水线在 Step 2 / 4 / 6 留了三个人工确认断点，设计意图是"发现问题及时人工修正"。
但断点只问"是否继续"，没说这一步能改什么、改了会不会生效。本次故障正是
用户在 Step 4 做了一个看起来合理的操作（移走封面图），却留下了半截状态。

更糟的是，各步骤实际读取的数据来源并不一致，有些手改根本不生效：

| 步骤 | 读取来源 | 手改是否生效 |
|------|----------|--------------|
| Step 2 翻译 | 内存里的 `zh_markdown` | `_zh.md` 改了**不生效** |
| Step 4 OSS 上传 | 内存里的 `image_map` | 移图片生效；`_en.md` 生效 |
| Step 5 格式转换 | 磁盘 `_en.md` + `images_map.txt` | `_en.md` 改了**生效** |
| Step 6 上传 PR | 磁盘 `blog_output/*.md` | 改了**生效** |

也就是说"改英文标题/正文"一直是可用的（Step 4 断点处编辑 `_en.md` 即可），
只是从没有人告诉用户；而"改中文"则是真的不生效——改了会被静默忽略。

### 3.2 修复

**让 `_zh.md` 的手改真正生效**（`main.py` 新增 `_read_edited_zh()`）：

断点放行后重读 `_zh.md`，与下载时写入的内容比对。判断方式是把内存里的
`(title, body)` 复原成 `"# {title}\n\n{body}"` 再与磁盘内容比较——
不依赖 mtime，因为编辑器保存后 mtime 必然变化，无法区分内容是否真的变了。
检测到改动就改用新内容翻译，并打印提示。改空或读取失败则回退原内容。

连带修了一个隐患：`_en.md` 的文件名原本用 `title` 生成，若用户改了中文标题，
就会和 `_zh.md`、`images_map.txt` 不同名，一次运行产出两套文件名。
现在文件名固定用 `original_title`，只有译文标题跟着变。

**三个断点都加上"这一步可以改什么"**，明确写出改哪个文件、改了什么效果、
什么不要碰。Step 4 的提示尤其重要：

```
   ── 这一步可以改什么 ──
     【改英文标题 / 正文】
       编辑: ...\xxx_en.md
       第 1 行 # 后面就是最终标题，正文随意改 —— Step 5 直接用这个文件，改了就生效
     【删掉多余的图】封面图/装饰图没被自动过滤掉时:
       把图片文件移进 ...\images\_filtered\
       → 只移文件即可，Step 5 会自动删掉正文里对应引用，不用手改任何文本
     【替换某张图】用同名文件覆盖 ...\images\ 里的原图
     【什么都不改】直接按 1 继续
   ⚠️ 别手改 images_map.txt（图片路径表），它由程序维护；
      图片增删一律用「移文件」的方式，避免正文引用和实际文件对不上。
   ℹ️ 图片一旦传到 OSS 不便撤回，所以确认放在这一步；
      文字的修改不着急，Step 5 之前任何时候都还来得及。
```

配合第 1 节的代码修复，"移文件"从一个会炸的操作变成了受支持的正规操作——
这是本轮最关键的改进：**人工修正不必面面俱到，少改比多改安全。**

### 3.3 未覆盖

`category`（文章分类）在 Step 4 由 LLM 从中文原文判定后直接传给转换函数，
不读文件，所以中途改不了。要改只能在 Step 6 编辑 `blog_output` 的 frontmatter。
提示里没写这条——写"能改"是假的，写"不能改"又显啰嗦，留待后续决定。

## 6. 关于 PR 合并权限（调研记录）

顺带查清了合并权限，备查：

| 项目 | 状态 |
|------|------|
| 账号在 deepmodeling/blog 的权限 | `maintain`（含 write） |
| master 分支保护规则 | 无（branch protection 404、rulesets 为空） |
| 必需 review | 无 |
| 允许的合并方式 | 仅 squash（merge commit / rebase 均关闭） |
| 仓库 auto-merge 开关 | 已开启 |

结论：有权限直接合，没有必需 review 卡着。流水线目前只做到"创建 PR"
（`github_uploader._create_pr()` 调 `gh pr create`，没有 `gh pr merge`），
合并需手动：

```
gh pr merge <PR号> --repo deepmodeling/blog --squash --delete-branch
```

或在网页点 Squash and merge。合并后 `push.yml` 的 deploy 任务才会执行
（条件是 push 到 master），几分钟后上线。

**暂不做成自动**：该仓库是公共组织仓库，合并即对外发布，PR 也是他人 review 的入口。
若后续要自动化，建议加 `config.yaml` 开关（如 `github.auto_merge: false`）
而非默认开启。
