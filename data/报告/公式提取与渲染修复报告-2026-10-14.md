## 1. 现象与定位

### 已发布正文里的五处空位

| 位置 | 已发布版本的内容 |
|------|-----------------|
| 带隙 | `Its bandgap is approximately ()` |
| 响应区间 | `In the near-infrared–visible light response range of ,` |
| 位移电流峰值 | `peak values exceeding Å` |
| 二维短路电流密度 | `reaches , .` |
| 提升幅度 | `increased by over (136%) and (158%)` |

最后一行是线索：`(136%)` 和 `(158%)` 括号内留着数、括号外为空。这个形态说明
原文句子结构是「提高超过 X (136%)」——括号内是补充说明，括号外才是正式数值。

### 定位：数值在 HTML 的属性里，不在图片里

最初的猜测是「数值被排版成图片，文字层没有」。抓取微信原文 HTML 后推翻了这个判断——
数值在 `<mjx-container>` 自定义元素的 `data-formula` 属性中，是纯文本：

```html
<mjx-container jax="SVG" role="presentation"
  data-formula="0.98\ \mathrm{eV}"
  data-formula-type="inline-equation"> … SVG … </mjx-container>
```

五处全部找到：

```
0.98\ \mathrm{eV}
(1-3\ \mathrm{eV})
3.0\ \mathrm{mA\cdotÅ/V^2}
J_x^{2\mathrm D}=31.43\ \mathrm{nA/m}
J_y^{2\mathrm D}=43.60\ \mathrm{nA/m}
```

用户提供了两张原文截图佐证（`data/微信原文截图.png`、`data/微信原文截图2.png`），
其中 `(0.98 eV)` 与上面的 `data-formula` 完全对应。

### 各版本对比：流水线本身无损

| 版本 | 数值状态 |
|------|---------|
| 微信原文 HTML | `()` 空位（数值在属性里，未进文字层） |
| `_zh.md` | `()` 空位 |
| `_en.md` | `()` 空位 |
| `blog_output/*.md` | `()` 空位 |
| GitHub 博客仓库 | `()` 空位 |

`blog_output` 与仓库文件逐字节一致（`diff` 验证），说明**每一步都是保真的**。
问题出在源格式未被识别，而非某个环节处理失误。

## 2. 缺陷一：下载器漏掉 `<mjx-container>`

### 原因

`_extract_formula()` 只认两种形态：

- `<script type="math/tex">`（含 `mode=display` 变体）
- `<span data-math>` / `<span data-latex>` / `<span class="mjx-*">`

而新版微信编辑器输出的是 **`<mjx-container>` 自定义元素**——既不是 `script` 也不是
`span`，三重判断全部落空。`data-formula` 这个属性名也不在检查列表里
（代码读的是 `data-math` / `data-latex`）。

实测该文章：`<script type="math/tex">` 0 个、`<span class="mjx-*">` 0 个、
`<mjx-container>` 5 个。**旧代码识别的格式一个都不存在**，所以五处全空。

### 修复

三处各加一个分支（`downloader.py`）：

- `_extract_formula()`：识别 `mjx-container`，读 `data-formula`；
  `data-formula-type` 含 `block`/`display` 输出块级 `$$…$$`，否则行内 `\(…\)`
- `_has_nested_formulas()`：追加 `find('mjx-container', attrs={'data-formula': True})`
- `_replace_nested_formulas()`：追加对应的 `find_all` 替换，保证占位符流程覆盖新格式

第二、三处缺一不可——只改 `_extract_formula` 的话，`_has_nested_formulas` 返回 False，
`_replace_nested_formulas` 根本不会被调用。

### 修复过程中的自纠

合成用例（覆盖所有分支）抓到一个真实缺陷：块级判断最初写的是
`'display' in formula_type`，但微信用的是 `block-equation`，会把块级公式误判成行内。
改为 `any(kw in formula_type for kw in ('block', 'display'))`。

这个缺陷在真实文章里**看不出来**——那篇文章五处公式全是行内，暴露不了。
只有写覆盖全分支的合成用例才会命中。

## 3. 缺陷二：渲染路径选错（codecogs → MathJax）

### codecogs 方案的问题

转换器原先把公式转成外链图片：

```html
<img src="https://latex.codecogs.com/svg.image?\inline ..." style="vertical-align:middle" />
```

三个问题，按严重程度排列：

**（1）深色模式不可见。** 实测 codecogs 返回的 SVG：

```
fill 取值        : ['currentColor']
是否有背景 rect  : False
硬编码颜色       : 无
内联 <style>     : False
```

图形用 `fill="currentColor"`，但作为 `<img>` 加载时 SVG 是**独立文档**，继承不到
父页 CSS 变量，`currentColor` 回退为初始值（黑）。而站点：

- `_config.next.yml` → `darkmode: true`
- dark 背景 `--body-bg-color: #282828`
- 主题 CSS 中针对 `img` 的 `invert`/`filter` 规则：**0 条**（不做反色补偿）

结果：深色模式下黑字画在深灰底上，公式基本看不见。

**（2）检测时序错误。** `convert_article()` 的执行顺序是：

```
132 行  body = self._convert_latex_to_html(body)     ← 公式已被转成 <img>
151 行  frontmatter = self._build_frontmatter(..., body)
539 行      has_math = self._has_math_formula(body)  ← 此时 body 里已无公式记号
```

`_has_math_formula()` 只认 `$$` 和 `$…$`，在转换**之后**执行，恒返回 False，
`mathjax: true` 永远不加。等于自己关掉了自己的开关。

**（3）仓库用例为 0。** 104 篇已发布文章中，codecogs 用例 0 篇，`$…$` + MathJax
用例 19 篇。codecogs 这条路径从未真正上线过，属未经生产检验的分支。

### 顺带发现：`mathjax: true` 是有效开关

过程中曾误判「`mathjax: true` 是废开关」，理由是站点 `_config.next.yml` 里
`math.mathjax.enable: true` 似乎全局生效。实测线上页面推翻了这一判断：

| 文章 | frontmatter | 线上 `enableMath` |
|------|-------------|-------------------|
| abacus_ai | `mathjax: true` | true |
| deepspin | `mathjax: true` | true |
| LibRI | `mathjax: true` | true |
| ABACUS_2026_09_04 | 无 | false |
| ABACUS_2026_09_01 | 无 | false |

主题 JS 首行是 `CONFIG.enableMath && (…)`——**它是总闸**，逐页由 frontmatter 控制。
所以 `mathjax: true` 是必需的，不是装饰。

### 分隔符：必须用 `$…$`，不能用 `\(…\)`

同样在过程中被推翻的判断。实测线上 HTML：

| 源文件写法 | 线上实际内容 | 结果 |
|-----------|-------------|------|
| `deepspin.md`: `\(10^{-4}\)` | `(10^{-4})` | 反斜杠被剥，渲染失败 |
| `abacus_ai.md`: `$O(N \ln N)$` | `$O(N \ln N)$` | 完整保留，渲染正常 |

机制是 CommonMark 的转义规则：`(` 属于可转义标点，`\(` → `(`；而 `\l`、`\m`
不是标点，原样保留。所以 `\(…\)` 写的公式在浏览器端收到的是残缺文本，
MathJax 根本不会处理。

这个差异**在源文件里看不出来**，只有对比线上 HTML 才能发现。

### 修复

`converter.py`：

- `_convert_latex_to_html()` → `_normalize_latex()`：只做分隔符归一化，
  不再生成图片。`\(…\)` → `$…$`，`\[…\]` → `$$…$$`，`$$`/`$` 原样保留
- `_has_math_formula()`：扩展支持 `\(…\)` 和 `\[…\]` 两种原始形态
  （下载器从 `data-formula` 提取出的正是这个形态，旧实现检测不到）
- 时序修复：`has_math` 在归一化**之前**计算，作为参数传给
  `_build_frontmatter(has_math=…)`，不再在转换后重新检测

### 代码块内的 `$` 是否会被误伤

担心过 shell 变量（`$BUILD_DIR`）被当成行内公式。实测排除：

- MathJax 的 `skipHtmlTags` 默认含 `code`/`pre`，代码块受保护
- 逐行核对存量文章：`ABACUS_24_06_2025.md` 有 80 处 `$`，代码块外仅 1 处，
  且是反引号内联代码，同样受保护
- `dp_v3_tutorial3.md`（唯一同时含 `mathjax: true` 和 `$VAR` 的文章），
  那处 `$CONDA_PREFIX` 在 ```` ```bash ```` 围栏内

`_normalize_latex` 只匹配 `\(…\)` 和 `\[…\]` 这两个明确的分隔符，不碰裸 `$`。

## 4. 过程中的三次误判

如实记录，因为都是「只看配置没验线上」导致的：

| # | 误判 | 推翻了它的证据 |
|---|------|---------------|
| 1 | 数值被排版成图片，文字层没有 | 抓原文 HTML，数值在 `data-formula` 属性里 |
| 2 | `mathjax: true` 是废开关 | 逐页对比线上 `enableMath`，实际是总闸 |
| 3 | `\(…\)` 能渲染 | 对比 `deepspin.md` 源文件与线上 HTML，反斜杠被剥 |

共同的教训：**配置声明 ≠ 线上行为**。这三条都只有抓取线上页面才能证实。
